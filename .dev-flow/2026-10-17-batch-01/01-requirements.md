## 1. Introduction

### 1.1 Purpose
The live contract for batch 2026-10-17-batch-01: the scale label (`Mondays · 1 day = 2 cells`, `Mondays · .5 d/cell`, …) leaves the tick row of the gantt view and of the presentation; both views label their tick row by one rule that names the selected task.

### 1.2 Scope
In: the tick row's label column in the gantt view (`3`, including link mode, which paints the same frame) and in the presentation (`R`, and so its `x` export); the deletion of `_gantt_scale_label`. Out: the tick cells themselves and the cadence rule (`gantt_cadence`, LLR-102.1), the month row, every other view's own date scale (the wave and agenda views paint their own, unrelated to this label), the wording `selected: no dates` (its approval is a separate open backlog item), the README hero image `docs/taskboard-gantt.svg` (it shows `Mondays · 1 d/cell` at line 157, but it is a static file generated by batch 2026-10-02-batch-01's `make_readme_gantt.py`, not painted by the app; regenerating it re-renders the whole board with every change since then — a docs change outside the commission, carried to `BACKLOG.md`), pushing to any remote.

## 2. Overall description

### 2.1 Product perspective
Both views build the tick row with the same builder (`gantt_day_row`) and differ only in how they label it; this batch makes the label one function.

### 2.2 Product functions
1. The tick row's label names the selected task (or carries the echo's own dates, or says the task has no date), in both views.
2. With nothing selected the label column of the tick row is blank.

### 2.3 User characteristics
One operator reading the gantt view at a terminal 80–118+ columns wide, or presenting a project to a room with `R`; keyboard-only. The task: see when the selected task falls on the axis — and, presenting, point the room at it — by reading the bright dates on the tick row, which the label names.

### 2.4 Constraints
Textual + Rich as shipped; no new dependency; every row exactly `width` cells (S1); the presentation's PRES-R2 oracle frames (cursor on `tw3`) unchanged.

### 2.5 Assumptions and dependencies
The fixtures `tests/kg_board.py` (the gantt oracle board) and `tests/present_board.py` (the PRES-C board) stay as they are.

## 3. High-level requirements (HLR)

### HLR-1701 — The tick row's label names the selection, never the scale
- **Traceability:** US-1701
- **Ledger:** LED-2026-10-17-batch-01.1, LED-2026-10-17-batch-01.2, LED-2026-10-17-batch-01.3
- **Statement:** When the gantt view or the presentation paints its tick row, the system shall label it, in the label column, `selected task ▸` in the echo's tone, bold, when the selected task has a date and the echo's own date text fits in the field; the echo's full text followed by ` ▸`, in the echo's tone, bold, when it does not fit; `selected: no dates` in `dim` when the selected task has no date; and nothing (a blank label column) when no task is selected; and the system shall never paint the scale text in either view, nor in the presentation's export. In link mode the candidate is the selection; a selected task a search filter hides is no selection to the frame (the app then moves its selection to a drawn task, or to none when the search draws no task); a selection whose dates lie outside the window keeps its echo at the window's edge and its label.
- **Rationale (informative):** the operator: «hay que quitarla. No agrega valor»; one rule in both views avoids two dialects.
- **Validation:** `test`
- **Executed verification:** `python -m pytest -q -p no:cacheprovider tests/test_tick_label.py tests/test_present_room.py tests/test_present_rulers.py tests/test_gantt_board.py tests/test_present.py`
- **Numeric pass threshold:** every arm passes; AT-1701 at 118×31 and 80×25, each arm driven by keys and board files only: (1) `3` on `kg_board` — the app selects the first drawn task — the painted tick row's label reads `selected task ▸`; (2) then `L` (link mode, the first candidate) → `selected task ▸`; (3) then `esc`, `/` `Daily` `enter` — the search keeps one open task (`Daily revenue model`) and the app selects it: the tick row (below the two search-bar rows) still reads `selected task ▸`; then `/`, the query replaced by `zzqx`, `enter` — no task holds it: the label column of the tick row is blank and the month row still holds `today`; (4) a board file with projects and no task, `3` → blank, `today` on the month row; (5) `kg_board`, `R` → the presentation's tick row reads `selected task ▸`; in every painted row of every arm the scale-text pattern finds 0 matches. TC-1701 covers the dateless, too-long, off-window, search-hidden, link-mode and no-cursor cases at renderer level. The PRES-R2 frames still equal the painted presentation (TC-1001, TC-1002).
- **Priority:** medium
- **Acceptance (black-box) — the user-verified outcome (the WHAT):**
  - **Observable outcome:** `3` with a task selected → the third painted row starts (after its right-aligned padding) with `selected task ▸`; `L` → the same for the candidate; a search that draws no task, or a board with no task → that row's label column is blank; `R` → the same rule; nowhere `Mondays ·`, `d/cell` or `cells`.
  - **Shipped surface:** key `3` → the board panel `#board` in gantt mode; key `L` → `GanttLinkMode` `#glink-frame`; key `/` → the search prompt; key `R` → `PresentScreen` `#present-frame`.
  - **Acceptance test(s):** AT-1701
  - **Boundary catalog (QC-3):** ☑ empty (no selection: a board with no task, a search that draws none, link mode with no candidate → blank; in the presentation a project with no open task, or every task hidden with `space` → blank) ☑ boundary (80×25 / 80×24 with a 20-cell label; an echo too long for the field → its own text; a dateless selection; a selection outside the window; a search that hides the selection) ☐ invalid — none: the label takes no input text ☐ error — none: no failure path
  - **Negative control:** on the base tree (`d79a33e`) AT-1701 arm (1) is RED: `views.py:3001-3006` labels a fitting echo with `_gantt_scale_label(...)`, so the painted label is the scale text — executed and captured at increment 001 (`evidence/red-001.txt`).

## 5. Validation strategy

### 5.1 Methods

> **Two layers** (per the Two-layer validation rule). Every batch declares BOTH:
> - **Layer A — white-box / functional (`TC-NNN`):** validates the HLR/LLR mechanism (the HOW). Methods: `test`, `inspection`, `analysis`.
> - **Layer B — black-box / behavioral acceptance (`AT-NNN`):** validates the user story's outcome through the shipped surface (the WHAT). Method: `acceptance`.

Layer A: TC-1701 (renderer level: `render_gantt`, `render_present`, `save_present_svg`). Layer B: AT-1701, the real app headless (`run_test`): `3` (and `R`) pressed, the painted rows read.

### 5.2 Batch acceptance criteria
- the LLR has a passing TC; the story a passing AT driving the shipped surface;
- every new assertion RED on the base tree or by a recorded mutation;
- the pinned tests of earlier batches that assert the scale text are updated law-driven and named (B1);
- the full suite green but for the known base failures, transcript under the batch's evidence;
- real-app captures (SVG) at 118×31 and 80×25 of the gantt view with a task selected, with none, and with a dateless task selected, and of the presentation with every task hidden (no cursor); one PNG at 118×31 of the gantt view with a task selected; under the batch's evidence. The tone is asserted by TC-1701 from the markup; the packet reads it from the SVG fills.
